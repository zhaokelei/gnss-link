# 技术方案

## 1. 整体链路

```
┌──────────── A 手机 ────────────┐          ┌──────────── B 手机 ────────────┐
│                               │          │                               │
│  LocationManager              │          │  ReceiveService (前台服务)      │
│   ├ gps provider   ──1Hz──┐   │          │    └ UDP :7007 收包             │
│   └ network provider ─────┤   │          │         │                     │
│                           ▼   │          │         ▼                     │
│  SendService (前台服务)        │  UDP     │  MockLocationEngine           │
│   ├ LocationFrame (JSON)  ────┼─────────►│    ├ addTestProvider("gps")   │
│   ├ 广播 WHO 做发现            │◄─────────┼────┤ addTestProvider("network")│
│   └ 收 ACK 算 RTT             │  ACK     │    └ setTestProviderLocation  │
│                               │          │         │                     │
└───────────────────────────────┘          │         ▼                     │
                                           │  LocationManagerService       │
                                           │   （系统层，替换真实定位）      │
                                           │         │                     │
                                           │         ▼                     │
                                           │  高德 / 百度 / Google 地图     │
                                           └───────────────────────────────┘
```

关键点：**B 端不"伪造 GPS 硬件"，而是顶替系统的 Location Provider**。
一旦 `addTestProvider("gps")` 成功，系统里名为 `gps` 的提供者就被换成了我们的测试提供者，
所有读取位置的应用拿到的都是我们灌进去的坐标，跟有没有 GPS 芯片无关。

## 2. 模拟位置的完整调用链

```kotlin
// 1. 顶替系统 provider（只需一次）
locationManager.addTestProvider(
    "gps",
    false,  // requiresNetwork
    false,  // requiresSatellite  ← 传 false，没有 GPS 硬件的设备也能用
    false,  // requiresCell
    false,  // hasMonetaryCost
    true,   // supportsAltitude
    true,   // supportsSpeed
    true,   // supportsBearing
    Criteria.POWER_LOW,
    Criteria.ACCURACY_FINE
)
locationManager.setTestProviderEnabled("gps", true)

// 2. 每次收到数据注入一帧
val loc = Location("gps").apply {
    latitude = frame.lat
    longitude = frame.lon
    accuracy = frame.accuracy.coerceAtLeast(1f)
    speed = frame.speed
    bearing = frame.bearing
    time = System.currentTimeMillis()                    // 必须非 0
    elapsedRealtimeNanos = SystemClock.elapsedRealtimeNanos()  // 必须非 0，且必须是本机时钟
}
locationManager.setTestProviderLocation("gps", loc)
```

三个容易踩的坑：

1. **`time` 和 `elapsedRealtimeNanos` 必须设置**，否则 `setTestProviderLocation` 抛
   `IllegalArgumentException: incomplete location`。`elapsedRealtimeNanos` 只能用**本机**的
   `SystemClock.elapsedRealtimeNanos()`，不能把 A 手机的时间戳直接搬过来。
2. **`accuracy` 必须 > 0**，传 0 也会抛异常。
3. **`removeTestProvider` 之后系统会自动恢复真实 GPS**，所以 App 退出/服务停止时一定要调，
   否则 B 端会一直"卡"在最后一个模拟点上，直到重启。

## 3. 为什么必须手动授权

`setTestProviderLocation` 要求调用者满足下列之一：

- 持有 `android.permission.ACCESS_MOCK_LOCATION` —— 这是 **signature|development** 级权限，
  只有系统应用或 adb 能拿到，普通 APK 申请了也无效（参考项目在 Manifest 里声明了它，其实没作用）；
- 或者被用户在「开发者选项 → 选择模拟位置信息应用」中指定。

系统把这个授权记录在 AppOps 的 `android:mock_location` 操作上，可以用代码查询但不能用代码修改：

```kotlin
val ops = getSystemService(AppOpsManager::class.java)
val mode = ops.unsafeCheckOpNoThrow(
    AppOpsManager.OPSTR_MOCK_LOCATION, Process.myUid(), packageName
)
val authorized = mode == AppOpsManager.MODE_ALLOWED
```

**这是 Android 的安全设计，没有绕过的办法。** 已 root 的设备可以：

```bash
adb shell appops set top.wxip.gpslink android:mock_location allow
```

注意 `ACCESS_MOCK_LOCATION` 在 Manifest 里声明虽然无效，但保留声明可以避免某些 ROM 的
兼容性问题，且方便 lint 明确意图（本工程加了 `tools:ignore`）。

## 4. 坐标系：一个必须说清楚的点

| 坐标系 | 用在哪 |
|---|---|
| **WGS-84** | GPS 原始输出、Android `Location`、国际标准 |
| **GCJ-02**（火星坐标） | 高德、腾讯、Google 中国、国内大部分地图 SDK 的对外接口 |
| **BD-09** | 百度地图 |

**Android 的 `LocationManager` / `FusedLocationProvider` 输出的永远是 WGS-84。**
地图 App 拿到系统定位后，自己内部做 WGS-84 → GCJ-02 的偏移。

所以：

- 我们注入的必须是 **WGS-84**，也就是 A 端 `Location` 里拿到的原始值，**不做任何转换**；
- 如果你从高德/百度 SDK 的逆地理、POI 搜索里拿到一个坐标（那是 GCJ-02/BD-09），
  直接灌进去，B 端地图上会稳定偏移 **300~700 米**，而且方向不固定，很难 debug；
- 真要跨坐标系，得先反算：GCJ-02 → WGS-84 用迭代逼近（没有解析解），BD-09 → GCJ-02 有公式。

本工程的 `LocationFrame` 全程透传 WGS-84，就是为了避开这个坑。

## 5. 延迟与平滑

链路上的延迟分四段：

| 环节 | 典型耗时 | 说明 |
|---|---|---|
| A 端 GPS 采样 | 0~1000 ms | 1Hz 刷新，平均 500ms |
| 序列化 + UDP 发送 | <1 ms | 单包 200 字节左右 |
| 局域网传输 | 2~15 ms | 5GHz Wi-Fi 更稳 |
| B 端注入 | <1 ms | 主线程外执行 |

端到端大约 **0.5~1 秒**。这个量级对导航基本无感，因为导航软件的转向提示本身就有几十米提前量。

如果以后要走公网中继，延迟会升到 100~300ms，这时候建议在接收端做**短时外推**：

```kotlin
// 用上一帧的 speed/bearing 推算当前位置，最多外推 2 秒
val dt = min((now - lastArrival) / 1000.0, 2.0)
val d  = speed * dt
val dLat = d * cos(bearingRad) / 111_320.0
val dLon = d * sin(bearingRad) / (111_320.0 * cos(latRad))
```

注意别外推太久，否则转弯时会"飘出路面"。本工程暂不启用，因为 1Hz 注入和真机 GPS 的
行为一致，导航 App 自身的滤波已经够用。

## 6. 前台服务与功耗

Android 8 以后，后台进程会被 `cached` / `frozen`，位置回调直接停。
参考项目把逻辑写在 `Activity` 里，**息屏 1~2 分钟就失效**，这是它最致命的问题。

本工程两个服务都声明为 `foregroundServiceType="location"`：

```xml
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_LOCATION" />
<service android:name=".service.SendService"
         android:foregroundServiceType="location" />
```

Android 14 起，`location` 类型的前台服务在启动时**必须已经持有 ACCESS_FINE_LOCATION**，
否则直接抛 `SecurityException`。所以启动服务前一定要先拿到运行时权限。

功耗实测参考（1Hz、精度优先）：

- A 端持续 GPS：约 **4~8% / 小时**，屏幕熄灭后会低一些；
- B 端只做 UDP 收包 + 注入：几乎可以忽略，**<1% / 小时**。

想再省电可以把采样间隔调到 2000ms、`minDistance` 设为 1m，但导航观感会明显变差。

另外建议引导用户把 App 加入"电池优化白名单"（国产 ROM 还需要单独在系统管家/自启动里放行），
否则部分 ROM 会在锁屏后杀掉前台服务。

## 7. 局域网传输的坑

**为什么选 UDP 而不是 TCP：**

- 定位是"最新值有效"的数据流，丢一帧完全无所谓，重传反而让数据变旧；
- UDP 无连接，A 端换网络/重启不需要重连握手；
- 单包 <1400 字节，不涉及分片。

**但 UDP 也有坑：**

1. **AP 隔离（客户端隔离）**：很多公共 Wi-Fi 和部分家用路由默认开启，两个客户端之间
   完全不通，广播也收不到。判断方法：A ping 不通 B 就是这个问题。解决：关掉 AP 隔离，
   或者 A 开热点让 B 连。
2. **广播被丢弃**：`255.255.255.255` 在部分路由上会被拦。本工程同时向各网卡计算出的
   子网广播地址发送（`NetworkInterface.getInterfaceAddresses().broadcast`），提高命中率。
3. **定向广播**：某些 Android 版本对 `192.168.1.255` 这种定向广播有限制，所以两个都发。
4. **IPv6**：本工程只用 IPv4，`InetAddress.getByName()` 可能返回 IPv6 地址，
   需要时用 `Inet4Address` 过滤。

**房间码的作用**：局域网里任何设备都能往 7007 端口发包。没有房间码校验，
隔壁工位的同事随手跑个脚本就能把你的手机"传送"到任何地方。本工程对 `sid` 不匹配的包直接丢弃。

## 8. 兼容性

| 项目 | 说明 |
|---|---|
| minSdk | 26（Android 8.0），`Location` 的 `verticalAccuracyMeters` 等接口从 26 才有 |
| targetSdk | 34 |
| Android 12+ | 申请精确位置必须**同时**申请 `ACCESS_FINE_LOCATION` 和 `ACCESS_COARSE_LOCATION`，只申请前者会被系统忽略 |
| Android 13+ | 前台服务通知需要 `POST_NOTIFICATIONS` 运行时权限 |
| Android 14+ | `location` 类型前台服务需要 `FOREGROUND_SERVICE_LOCATION` 权限且已持有定位权限 |
| 无 GPS 硬件 | 可以工作。`addTestProvider` 创建的提供者不依赖硬件，但部分 ROM 上 `gps` 提供者不存在时会失败，所以本工程同时顶替 `network` |
| 国产 ROM | MIUI/ColorOS/EMUI 等需要额外允许"后台弹出界面""自启动""锁屏显示"，否则前台服务可能被杀 |

## 9. 安全与合规

位置信息在国内属于**敏感个人信息**（《个人信息保护法》第 28 条），处理需要单独同意。
本项目是自用工具，但如果要分发给他人：

- 共享方必须明确知道自己的位置正在被发送（前台常驻通知就是为此）；
- 不要做"静默上传"；
- 明确禁止的用途：考勤代打卡、网约车刷单、游戏外挂、伪造行程证明——
  这些在多数平台规则和司法实践中都可能被认定为欺诈。

技术上还可以再加一层：房间码派生 AES 密钥对 payload 加密，防止同网段抓包重放。

## 10. 调试技巧

```bash
# 查模拟位置授权状态
adb shell appops get top.wxip.gpslink android:mock_location
# 免手动设置（需 root 或 debug 包 + adb）
adb shell appops set top.wxip.gpslink android:mock_location allow

# 看系统当前认为的位置
adb shell dumpsys location | grep -A3 "last location"

# 看本工程日志
adb logcat -s MockEngine SendService ReceiveService

# 模拟器里造一个 GPS 点（用来测试 A 端）
adb emu geo fix 121.473701 31.230416
```

验证是否生效的最快方法：B 端打开任意地图 App，看蓝点是不是跳到了 A 的位置；
或者在 B 端装一个 `GPS Test` 之类的工具，看 `Location.isMock()` 是否为 `true`。
